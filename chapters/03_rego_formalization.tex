\chapter{Formal Specification of Rego}
\label{ch:form}

This chapter provides formal specification of the Rego policy language used in OPA.
These definitions are derived from the official OPA reference \cite{opa:web} and the OPA source code \cite{opa:git}.
All examples of Rego policies are valid code, interpretable online at the official Rego Playground: \url{https://play.openpolicyagent.org}.

\section{Terms}
\label{s:terms}
%%=============================================================

This section describes values viable in Rego and defines their type system.

%%=============================================================
\subsection{Variables}
%%-------------------------------------------------------------
In OPA, the response document contains fields, which correspond to \emph{variables} specified in the respective Rego policy.
These fields are key--value pairs, where the key is the name of given variable.
Variable names are given by the regular expression $[\_a-zA-Z]\{\_a-zA-Z0-9\}^*$, with $\_$ being a reserved symbol for \emph{unnamed variables}.
We denote the set of all variables with $\Vars$ and the set of Rego values with $\Vals$.
In this paper, we will usually call variables $x,y$ or $z$ and denote values with $v_i$ for $i$ typically being a natural number,

Let $\sigma_V: \Vars \to \Vals$ be a \emph{substitution} mapping variables to Rego values.
We will sometimes abuse the notation of values in this paper by calling variables values.
Calling variable $x$ a value, will hold the meaning of saying $\sigma_V(x)$.

Variables in Rego can be either \emph{global} or \emph{local}.
Global variables are accessible throughout the whole policy, whereas local variables are rule-specific and do not appear in the output document.
Even though, local variables can \emph{shadow} global variables on name collision, we will not distinguish much between them, since the internal Rego compiler of OPA renames all local variables to unique names.
We denote the set of all global variables with $\Globals$ and the set of all local variables with $\Locals$.

%%=============================================================
\subsection{Atomic and Composite Values}
%%-------------------------------------------------------------
In Rego, values of variables can be of the given types:
\begin{itemize}
  \item \emph{Strings}: Sequences of ASCII characters enclosed in double-quotes, such as \texttt{"abc"}.
    \textit{Rego also supports prefixing strings with \$ symbol for creating so called template-string used for runtime interpolation, but we will not cover them in this work.}

  \item \emph{Numbers}: In Rego, this name, in accordance to the JSON format, represents either an unbounded whole number (\texttt{BigInt}), a whole 64-bit number or a floating-point number (64-bit double-precision as in IEEE 754).
    \textit{Creating a value which overflows the maximum/minimum floating-point value yields a $\Null$.}

  \item \emph{Booleans}: Either \true ($\top$) or \false ($\bot$) values.

  \item \emph{Null}: A special $\Null$ value, which does not belong to any other domain of values.
\end{itemize}

For the rest of this paper, we will call the values of the above types \emph{atomic}.
Rego also offers the support for \emph{composite types} (or composite values).
We will call such values \emph{collections}, and they can be of the following three types:

\paragraph{Arrays.}
Arrays are 0-indexed sequences of $n$ values, noted as $[v_0,\dots,v_{n-1}]$.
These arrays are \emph{heterogenous}, meaning that different values of an array do not have to be of the same type.
$[ ]$ is the special case of \emph{empty array}.

\paragraph{Objects.}
Object is a set of key--value pairs, noted as $\{v_{k_0}:v_{v_0},\dots,v_{k_n}:v_{v_n}\}$, where $n$ is its length.
Both keys and values can be of any type (even composite).
$\{\}$ is the special case of \emph{empty object}.

\paragraph{Sets.}
In Rego, sets of values are noted as $\{v_0,\dots,v_n\}$ and they are also heterogenous.
As $\{\}$ already denotes an empty object, Rego defines an empty set with \texttt{set()}.

To assign a value to a variable in Rego, the \texttt{:=} operation is typically used.\footnote{
  The Rego language allows assigning values to variables with either the assign symbol (\texttt{:=}), or the unification symbol (\texttt{=}).
  This paper only will only expect the prior version to be used, since it is the recommended option by the OPA reference \cite{opa:web}.
}
In this way, we can set out inference rules for variable values:
\[
\textbf{(AssignLiteralValue)}\quad
\inferrule{
  x := v
}{
  \sigma_V(x) = v
}
\qquad
\textbf{(AssignVarValue)}\quad
\inferrule{
  x := y
}{
  \sigma_V(x) = \sigma_V(y)
}
\]

\begin{figure}
  \label{fig:values}
  \begin{lstlisting}[language=Rego]
package example

n := 42
b := true
s := "Hello"

arr := [1,2,3]
obj := { "n": n, "b": b }
set := { n, b, s, true }
\end{lstlisting}
  \caption{Example Rego policy.}
\end{figure}

\begin{example}
  Consider the Rego policy given in figure \ref{fig:values}.
  The first line only specifies the policy package name and is not relevant in this case.
  This policy contains atomic values $n, b, s$ and composite values $arr, obj$, and $set$.
  The value $\sigma_V(n)$ is equal to $42$ and $\sigma_V(b) = true$.
  The length of $set$ is $3$, since its two members, $b$ and $\true$, have the same value.
\end{example}

\subsection{References and Undefined Values}
\label{ss:ref}
%%-------------------------------------------------------------

To access a value from collection, Rego supports a square bracket notation similar to other modern programming languages.
It is noted as $x[v]$, i.e., the value of $x$ at key $v$.
Since the input documents for policies are usually large and nested collections (typically objects), it is not unusual to see long chains of value such value accessing, such as $x[v_0]\dots[v_n]$.
As these constructs are typical for this policy language, they have a special name: \emph{references}.

To simplify their use, Rego offers an alternative dot notation.
This notation is used, when the reference accesses a collection with string literal.
With this alternative, the reference
$$ x["a"]["b"]["c"]["d"] $$
is identical to
$$ x.a.b.c.d $$

Additionally, for a policy package $\pkg$ and a global variable $x$, which is defined in it, reference \texttt{data.$\pkg$.x} accesses the value $x$, i.e., $\sigma{\texttt{data.\textit{$\pkg$}.x}} = \sigma(x)$.
In the compilation step of Rego execution, all global variables are transformed into this form.

It is also possible that given collection does not contain any value at the specified key, for which Rego reserves a special \emph{undefined} value.
Such value has specific properties, similar to \texttt{NaN} value in other programming languages.
The most relevant properties of this value is that two undefined values are not equal, and that all expression containing an undefined value are also undefined.
This means that also object literals containing even a single undefined value are undefined.

\begin{example}
  Let \texttt{a = [1,2,3]} and \texttt{o = \{"a": a\}} be defined in the package $\pkg$.
  Then the reference \texttt{o.a[0]} has value $1$ and references \texttt{o.b[0]} and \texttt{o.a[5]} are $\Undef$.
  In addition, the values of \texttt{data.$\pkg$.a}, \texttt{a}, \texttt{data.$\pkg$.o.a}, and \texttt{o.a} are equal.
\end{example}

\subsection{Type System}
\label{s:typ}
%%-------------------------------------------------------------

Each value in Rego has its corresponding type.
The set of \emph{Rego types} $\mathbb{T}$ is defined by the grammar:
\begin{align*}
\ty \;::=\; & \Str \mid \Int \mid \Bool \mid \Null \mid \Undef \mid \Unknown \\
   \mid\;   & \ty_1 \cup \cdots \cup \ty_m \\
   \mid\;   & \Array{\ty} \\
   \mid\;   & \RegoSet{\ty} \\
   \mid\;   & \Obj{v_1{:}\ty_1,\ldots,v_n{:}\ty_n}
\end{align*}
The intended meaning is standard:
\begin{itemize}
  \item \emph{Atomic types} $\Str, \Int, \Bool, \Null$ correspond to atomic values in Rego; $\Undef$ is also considered an atomic type and it corresponds to a special value of the same name (similarly to $\Null$),
  \item $\Unknown$ is a \emph{placeholder} type used when no information is available yet,
  \item $\ty_1 \cup \cdots \cup \ty_m$ is a \emph{union} type, modelling values that may inhabit any of the member types.
  \item $\Array{\ty}$ is an \emph{array type}, where $\ty$ is a union over all of its element types,
  \item $\RegoSet{\ty}$ is a \emph{set type}, of elements of type $\ty$ (similarly to the array type),
  \item $\Obj{v_1{:}\ty_1,\ldots,v_n{:}\ty_n}$ is an \emph{object type} with fields $v_i \in \Vals$ typed $\ty_i$.
\end{itemize}

\subsection{Function Calls and Terms}
\label{ss:term}
%%-------------------------------------------------------------

Rego has a handful of builtin \emph{functions} used for arithmetics, string and regex manipulation, aggregation of collections, graph operations, database queries, hashing, and much more.
Each of these functions have a designated name, a list of allowed parameter types, and a return type.
Some of the most common functions also support infix operators, such as $+, -, ==, \geq$, etc., but they are always rewritten to their function form (e.g., \texttt{plus(1,2)}) by the OPA compiler.

All functions allow the return value to be directly assigned into a variable with providing its name as an additional parameter.
We will call this an \emph{assign form} of a function.
In this manner, the expression
$$ x := 1 + 2 $$
is equivalent to the assign form
$$ \texttt{plus(1,2,x)} $$.
The internal compiler of this language \cite{opa:git} prefers the latter option whenever possible.
In this paper, we will prefer the first option for its ease of readability.

Formally said, a Rego function is defined as a triplet $f = (f_N, f_P, f_R)$, where:
\begin{itemize}
  \item $f_N$ holds the function name
  \item $f_P = \{(\ty_1,\dots,\ty_a) | a \in \Nat_0\}$ is a set of lists of parameter types, where $a$ is the function arity and $\ty_i \in \Types$ for $1 \leq i \leq a$,
  \item $f_R \in \Types$ is the return type.
\end{itemize}
We denote the set of all functions with $\Funs$.

In Rego, we use a special name \emph{term} for everything either holding a value, or being a function identifier.
This includes literals (strings, objects, etc.), variables, references, and function calls.
Recursively, both references and function calls are defined as a sequence of terms.
For the rest of this paper, we will denote the set of all terms with $\Terms$ and the value substitution mapping terms to values with $\sigma$.

For every function identifier $f$, we set $\sigma(f) = \Undef$.
We set a special function $\sigma_F: \Terms \to \Funs$.
Additionally, we declare a function $\typof: \Terms \to \Types$ mapping all terms to their corresponding types.

\begin{example}
  Consider the following Rego statement $\psi$:
  \begin{center}
    \texttt{x := [1, 2+3]}
  \end{center}
  The compiled version of such statement is
    \texttt{x := [1, plus(2,3)]}
  and it contains terms \texttt{x}, \texttt{1}, \texttt{plus}, \texttt{2}, \texttt{3}, \texttt{plus(2,3)}, \texttt{[1, plus(2,3)]} and a builtin function \texttt{plus}, where $\sigma_F(\texttt{plus}) = (\texttt{plus}, \{(\Int,\Int)\}, \Int)$.
  $\psi$ gives $\sigma(x) = [1, 5]$, and thus $\typof(x) = \Array{\Int}$.
\end{example}

\subsection{Expressions}
%%-------------------------------------------------------------

We briefly talked about expressions in the previous section, and now we will formally specify them.
Expression $e$ is either a term\footnote{
  Internally, expressions can be specifically set to be function calls, i.e., list of terms.
} which is evaluated into a boolean value (\emph{term expression}), or a declaration of local variable (\emph{declaration expression}).
Declared variable can be either \emph{assigned}, \emph{existentially quantified}, or \emph{universally quantified}.

An expression of term $t$, is evaluated as \true (it \emph{holds}), iff the $\sigma(t) \notin \{\Undef,\bot\}$, and as \false otherwise.
We denote the result of expression $e$ with $\Holds(e)$.
In contrast with other modern programming languages, this also means that $\Null$ or an empty string are evaluates as \true.

\section{Rules}
%%=============================================================

Every Rego policy is comprised of a set of rules $\Rules$.
Since it is a declarative language, we can truly treat specified rules as a set without a strict order.
Every rule $\Rule$ consists of a \emph{rule head} ($h$) and a list of \emph{rule bodies} ($B$), where the head specifies which term (non-literal) is set, and the body specifies a value to which it is set, and conditions (expressions) which need to be met for this assignment to be valid.

%%=============================================================
\subsection{Rule Head and Body}
%%-------------------------------------------------------------

Head $h$ is defined as a tuple $(h_n, h_k, h_a)$, where $h_n \in \Terms$ denotes its name, $h_k \in (\Terms \cup \Undef)$ denotes its \emph{key}, and $h_a = (a_1,\dots,a_n)$ is a (possibly empty) list of arguments for $n \in \Nat$.
We will often abuse the notation, and call variables heads.
For a rule with head $h = (h_n, h_k, h_a)$ we define a set of rules
We denote a rule with head $h$ as \emph{rule of $h$} and declare a set of all rules of $h$ as $P_h$.

We define body $B$ as a pair $(B_v,B_E)$, where $B_v \in \Terms$ is its value, and $B_E = (e_1,\dots,e_n)$ for $1 \leq i \leq n$ and $e_i$ being an expression.
When all expressions of rule body $B$ hold, we say that it is \emph{satisfied}, denoted as $\Holds(B)$.
Formally said, for a rule body $B$: 
$$\Holds(B) \iff \forall_{e \in B_E}: \Holds(e)$$.
Rules are defined as pairs $(h,B)$.

Every rule is written as $h$ $B_1$ \texttt{else} $\dots$ \texttt{else} $B_n$, with $h$ being the head and $B_i$ being the bodies, for $1 \leq i \leq n$, formally noted as a tuple $(h,B)$, where $B$ is the list of bodies $(B_1,\dots,B_n)$.
A body is written as a value possibly followed by either as a single expression $e$, or as $\{ e_1 \dots e_n \}$, where expression $e_i$ and $e_{i+1}$ are separated either by a semicolon (\texttt{;}) or a newline character, for $1 \leq i \le n$.
If the value of body $B$ is missing, it is implicitly \true.
If the body does not contain any expressions, it is automatically evaluated as valid.
In adition, the rule body $B_i$ is only evaluated if none of its \emph{predecessors} was satisfied, i.e., iff $\neg\exists_{j \in (0,i)}: $

\begin{figure}
  \label{f:e:body}
  \caption{Example of Rego policy with two rules containing different types of bodies.}
\begin{lstlisting}[language=Rego]
policy example

x if 1 < 2
y := 1 if {
  z := true
  x == z
} else := 2
\end{lstlisting}
\end{figure}

\begin{example}
  For example, consider the Rego policy $\phi$ depicted in figure \ref{f:e:body}.
  $phi$ contains two rules, one being the rule of $x$ and the other being the rule of $y$, meaning $|P_x| = |P_y| = 1$.
  The rule of $x$ contains a single body, which assigns it \true, iff the expression $1 < 2$ holds, which it does, since it is neither $\Undef$, nor \false.
  Thus $\sigma(x) = \true$.

  The rule of $y$ contains two bodies, where the first one assigns $1$ to the head $y$ if its two expressions hold: 1) declaration of local variable $z$, which is assigned to be \true (declaration always holds), and 2) comparison of equality between $x$ and $z$, where $\sigma(x) = \sigma(z) = \true$ and thus it also holds.
  The second body, which would unconditionally assign the value of its only body ($2$) to the head, is not evaluated, since the conditions of its predecessor were satisfied.
\end{example}

%%=============================================================
\subsection{Types of Rules}
%%-------------------------------------------------------------

Rego offers multiple different types of rules:
%%-------------------------------------------------------------
\subsubsection{Complete definitions.}
\emph{Complete definitions} (or \emph{complete rules}) define the whole value of rule head.
The rules in the prior example given in figure \ref{f:e:body} were all complete, since they assigned the values of their bodies directly into the head.
For such rules, we infer the value of the head with:
\[
\textbf{(CompRuleVal)}\quad
\inferrule{
  (h,B) \in \Rules
}{
  \Holds(B) \implies \sigma(h) = B_v
}
\]
A \emph{conflict} happens, when two different rules try to assign a different value to the same head, yielding the whole policy \emph{invalid}.

%%-------------------------------------------------------------
\subsubsection{Incremental definitions.}
% Sets
% Objects (conflicts)
\emph{Incremental definitions}, (or \emph{incremental rules}) define different parts (\emph{keys}) of the same head for each rule.
Going back to the definition of rule head $h = (h_n,h_k,h_a)$, for incremental rules, $h_k \in \Terms$ and $h_a = ()$, i.e., its key is defined and its list of arguments is empty.

Incremental rules are applicable for sets with special \texttt{contains} keyword (omitting rule body values) followed by the key and for objects with the head beign a reference, where only the last term is considered a key.
They are not applicable to arrays, as they need to be defined only with complete rules.
With incremental rules, a conflict can occur when two rules assign different values to the same key, which can effectively only happen for objects.

For terms $t,k \in \Terms$, providing an incremental rule for value $t$ at key $k$ is possible, iff $t$ is not defined completely by any other rule.
In this case, we not only say that $t$ is defined incrementally, but also that the value $t[k]$ is defined completely.

For a policy $\psi$, we note the set of all heads defined incrementaly as $\Inc$ and the set of all heads with a complete defintion as $\Comp$.
Since single head $h$ can be defined either completely or incrementally, we can say that $(h \in \Comp) \iff (h \notin \Inc)$.

\begin{figure}
  \label{f:e:inc}
  \caption{Example Rego policy containing incremental rules.}
\begin{lstlisting}[language=Rego,escapechar=|]
package example.incremental

x contains 1 |\label{inc:x1}|
x contains 2 if true |\label{inc:x2}|

y.a.b.c := false |\label{inc:y}|
# y := { "d": false } |\label{inc:y_}|

z[v] := true if { 
  some v in x 
  v > 1
}
\end{lstlisting}
\end{figure}

\begin{example}
  Consider the policy $\phi$ given in figure \ref{f:e:inc}.
  $\phi$ contains two incremental rules regarding $x$ on lines \ref{inc:x1} and \ref{inc:x2}, with keys $1$ and $2$ respectively.
  From these rules, we can infer $x$ to be a set, containing both keys, since the first one is contained automatically, since the body of this rule is empty, and for the second one, all expressions from its body hold.

  Line \ref{inc:y} contains a rule, which completely defines \texttt{y.a.b.c} to be \false, whilst incrementally defining \texttt{y.a.b} on key \texttt{c}.
  This means that also \texttt{y} and \texttt{y.a} are defined incrementally, and introducing their complete definition, e.g., uncommenting line \ref{inc:y_} would cause a collision.

  The last rule incrementally defines \texttt{z} on a variable key \texttt{v}.
  In the body of this rule, we see a two expressions: 1) a declaration of an existentially quantified variable $v$ over fields of $x$, and 2) a constraint on this variable.
  Informally speaking, this rule says: \textit{\texttt{z} contains any element of \texttt{x} which is greater than 1}.

  Evaluating all rules gives the value mapping $\sigma(x) = \{1,2\}$, $\sigma(y) := \{"a": \{"b": \{"c": \false\}\}\}$, and $\sigma(z) = \{1: \true\}$.
  Thus, the response document would contain three fields representing these variables.
\end{example}

\subsubsection{Default Rules.}
Default rule sets a fallback value $v$ for head $h$, where $\Rules_h \in \Comp$, meaning $\sigma(h) = v$, iff $\forall_{(h,B)}: \neg\exists_{b \in B}: \Holds(b)$.
We define a new function $\Def: \Terms \to \Vals$ mapping every head $h$ to its \emph{default} value $\Def(h)$.
Default rules are applicable at most once, only for heads with complete definition.
If a given head $h \in \Comp$ does not have a default rule, we set $\Def(h) = \Undef$.
