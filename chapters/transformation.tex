This section describes the transformation of Rego terms into SMT.
By the specification given in Chapter~\ref{ch:form}, terms can be either values, variables, references, or function calls.

Since we will operate with an \smtlib representation of terms, we define a set of valid SMT term encodings with $\STerms$.
% We set such encodings to also inherit the properties of terms, such as depth $\depth$ or type $\typof$.
During this section, we will iteratively refine the function $\encode: \Terms \to \STerms$.

\subsection{Type definition}

As \smtlib is a statically typed language, we need to firstly declare the sorts of encoded terms.
To avoid recursive types, we set a dedicated sort for each possible \emph{depth} $\depth$ of types given by the type analysis (given in Chapter~\ref{ch:typ}); the depth is defined as follows:
\begin{itemize}
  \item $\depth(\ty) = 0$, for $\ty$ being an atomic type,
  \item $\depth(\ty_1 \cup \cdots \cup \ty_m) = \depth(\ty_i)$, for $1 \leq i \leq m$, where $\forall_{1 \leq j \leq m}:\depth(\ty_i) \geq \depth(\ty_j)$,
  \item $\depth(\Obj{k_1{:}\ty_1,\ldots,k_n{:}\ty_n}) = 1+\depth(\ty_1 \cup \cdots \cup \ty_n)$,
  \item $\depth(\Array{\ty}) = 1+\depth(\ty)$,
  \item $\depth(\RegoSet{\ty}) = 1+\depth(\ty)$.
\end{itemize}
\textit{For the reason of better readability, this definition uses the improper notation of singleton types, where $\{t\}$ is denoted as $t$.
With the strict notation given in Section~\ref{ss:types:new}, the first case of this definition would be noted as: $\depth(\{t\}) = 0$ for $t$ being an atomic type.}

Informally said, atomic types have depth $0$, and composite types have their depth greater by one than their element with the maximum depth.
In addition, we allow for the type depth function $\depth$ to be applied directly to terms with the intuitive semantics: $\depth(t) = \depth(\typof(t))$, where $t \in \Terms$.
Since $\Unknown$ is not constrained, we set $\depth(\Unknown) = \infty$.

For a term $t$, we set the sort of its encoding $\encode(t)$ to be \texttt{$OTypeD_N$}, where $N = \depth(t)$.
The types $OTypeD_0$ and $OTypeD_i$ are iteratively refined throughout the Section~\ref{trans:ss:vals}.

\subsection{Variables}
\label{ss:vars:t}
%%-------------------------------------------------------------

In SMT, variables can be declared in the global scope with the \texttt{declare-fun} construct.
Since \smtlib has is a strongly-typed language, we need to provide sorts of variables during the declaration.
For $x \in \Vars$ we set a its sort to be \texttt{$OTypeD_N$}, where $N = \depth(x)$ as mentioned in the previous section.

Intuitively, the global scope will only contain global variables, i.e., variables $x \in \Globals$.
Hypothetically, for no clash in variable names, also local variables could be declared with mentioned \texttt{declare-fun} construct.
We will choose to only specify them locally as expected by the \rego semantics but with the main purpose not to let them pollute the output model.
For this cause, we will use the \texttt{let} construct for assigned local variables.
% For this cause, we will use the \texttt{let} construct for assigned variables, \texttt{exists} for existentially quantified variables, and \texttt{forall} for universally quantified variables.
Since the \texttt{let} construct does not specify the sort of given local variable, we need to make sure to always assign it a (typically symbolic) value of the expected type.

\subsection{Values}
\label{trans:ss:vals}
%%-------------------------------------------------------------

This passage reasons about the SMT sorts used to represent given Rego values.

%%------------------------------------------------------------
\subsubsection{Atomic Values}
%%.............................................................

For Rego constants of atomic types, we choose the transformation into the following \smtlib sorts.
For $\Str$ and $\Bool$, their default SMT variations are semantically equivalent since the sort String accepts Unicode characters.
For values of types $\Null$ and $\Undef$, we declare new sorts of the respective names.

The Rego type $\Int$ allows for its values to be either floating point or whole numbers, which would result in the corresponding SMT sort being an union between two options.
This is acceptable in \smtlib, with the possible types being \texttt{Float} and either \texttt{BitVec 64} or \texttt{Int}.
With my supervisor, we decided that for the current state of the presented tool, the support for floating point numbers can be omitted.
This decision is also backed up by the fact that values of this sub-type are not present in most of the reference policies \cite{rego-policies:web}.
The decided representation of $\Int$ is thus the default \texttt{Int} sort.

Since every atomic type $\ty$ is defined to have its depth $\depth(\ty) = 0$, we declare the sort for atomic values as:
\begin{lstlisting}[language=SMT,escapechar=|]
(declare-datatypes ()
  ((OTypeD|$_0$|
    (OString (str String))
    (ONumber (num Int))
    (OBoolean (bool Boolean))
    ONull
    OUndef
  )))
\end{lstlisting}

In the domain of $\STerms$ we define the depth of values of sorts \texttt{String}, \texttt{Int}, and \texttt{Boolean} to be $-1$, to reflect that it is not assignable to a variable of depth $0$.

%%-------------------------------------------------------------
\subsubsection{Composite Values}
%%.............................................................

The implementation of collections brings up difficulties, since by definition they can be infinitely nested, which would lead to a recursive datatype, which is a great bottleneck for a formal analysis, such as SMT solving.
As we have already defined a mechanism for capturing specific types of values and each type has a specific depth, we can restrict the SMT representation to operate only on values up to a set maximum depth.
Such sorts are defined in \smtlib in the theory of algebraic datatypes, which is transformable into the theory of uninterpreted functions.

As we described in the passage \ref{ss:vars:t}, we declare sorts of form \texttt{$OTypeD_N$}, where $N$ would be limited to the maximum depth of term type found for given policy, i.e.,
$$ N = \max_{t \in \Terms}(\depth(t)) $$

We have already established the atomic sort \texttt{OTypeD$_0$}; in this section we will iteratively define and refine the sort of a higher depth.

%%.............................................................
\paragraph{Objects.}
The support of objects is a crucial part to the whole analysis, since OPA communicates with the policies with structured documents, most prominently objects.
Fortunately, \smtlib supports the theory of arrays, where \texttt{(Array $T_1$ $T_2$)} maps keys of type $T_1$ to values of type $T_2$.
This behaviour perfectly corresponds to the semantics of Rego objects.

By the definition of a type depth $\depth$, every member of an object has strictly lower depth than the object itself.
But this does not apply for its keys, which is why we need to take them into account separately.

A possible solution would be to get the maximum depth of a key in all objects and simply define $T_1$ to be of this maximum depth for all object specified.
Even though this option allows to fully satisfy the needs of object keys, we decided to initially only support keys of the String sort, since other alternative appear in the reference policies very sparsely.
This is due to the property of the most relevant document format in OPA -- JSON -- where objects can only have string keys.

Thus we define an object of depth $N$ to have SMT sort:
\begin{center}
  \texttt{(Array String OTypeD$_{N-1}$)}
\end{center}

It is important to note that as the Array sort in \smtlib represents a total mapping, meaning we need to explicitly set all unmentioned keys to $\Undef$.
Fortunately, modern SMT solvers often support creation of so called \emph{constant arrays}, which map every key to the same value.
We can combine this construct with the \texttt{store} operation to create constant objects corresponding to Rego semantics, such as in figure \ref{f:cons-obj}.

\begin{figure}
  \label{f:cons-obj}
  \caption{\smtlib snippet for $\encode(\{\q{a}: 1, \q{b}: \true\})$.}
\begin{lstlisting}[language=SMT,escapechar=|]
(store
  (store
    (as-const (Array OTypeD|$_0$| OTypeD|$_0$|) OUndef)
    "a" (ONumber 1))
  "b" (OBoolean true))
\end{lstlisting}
\end{figure}

%%.............................................................
\paragraph{Arrays.}
Counterintuitively, the SMT Array sort does not properly represent the Rego $\Array{\_}$ type, since -- as already mentioned -- SMT Arrays are full mapping from the key domain, whereas Rego arrays only allow positive integers and only for a specific range starting with $0$.
For this cause, we implement this type with the \texttt{Seq} sort:
\begin{center}
  \texttt{(Seq OTypeD$_{N-1}$)}
\end{center}

%%.............................................................
\paragraph{Sets.}
Even though \ziii does not explicitly support a designated set theory, they are regularly represented as an array mapping from specified type to boolean, treating only values mapped to \true as defined.
We will use the constructor \texttt{(Set T)} in place for \texttt{(Array T Bool)} for better clarity.
\begin{center}
  \texttt{(Set OTypeD$_{N-1}$)}
\end{center}

%%.............................................................
\paragraph{Unaligned Collections.}
Since the designated sorts for collection specified above only allow to access values of the directly lower depth, we restricted the collections to contain only values of the same depth.
This is inadequate to the actual behaviour of composite types, which are allowed to be in this way \emph{unaligned}, such as with the object:
\begin{center}
  \texttt{\{ \q{D0}: 1, \q{D1}: \{ \q{foo}: \q{bar} \} \}}
\end{center}
For this cause, we specify a designated constructor to explicitly \emph{wrap} a sort into an incremented depth.
Thus the definition of the depth-specific sort is the following:
\begin{lstlisting}[language=SMT,escapechar=|]
(declare-datatypes ()
  ((OTypeD|$_N$|
    (Wrap|$_N$| (wrap|$_N$| OTypeD|$_{N-1}$|))
    (OObj|$_N$| (obj|$_N$| (Array String OTypeD|$_{N-1}$|)))
    (OArray|$_N$| (arr|$_N$| (Seq OTypeD|$_{N-1}$|)))
    (OSet|$_N$| (set|$_N$| (Set OTypeD|$_{N-1}$|)))
  )))
\end{lstlisting}

\subsection{References}
%%-------------------------------------------------------------

When dealing with references (i.e., collection accessing), we have to distinguish between different types of their \emph{bases} (defined in section \ref{ss:ref}).
In this paper, we will cover only the special case of \texttt{data.$\pkg$.x} which translates to the given variable \texttt{x}; all other bases are kept intact.

Iteratively, for each following term, we wrap the base with
\begin{enumerate}
  \item a selector specific for the type of given value,
  \item constructor to the actual sort domain of selected element.
\end{enumerate}

Since we will often need to modify the depth we define algorithms:
\begin{center}
  \begin{minipage}{0.44\textwidth}
    \begin{algorithm}[H]
      \SetKwInOut{Input}{input}\SetKwInOut{Output}{output}
      \caption{Wrap(t,d)}\label{alg:wrap}
    \Input{$t \in \STerms$, $d \in \Nat$}
    \Output{$t' \in \STerms$}
    \BlankLine
    $t' \leftarrow t$\;
    \If{$\depth(t) = -1$ \tcc*[r]{atomic}} {
      \uIf{$\typof(t) = \Int$}{
        $t' \leftarrow$ \texttt{(ONumber $t'$)}\;
      }
      \uElseIf{$\typof(t) = \Str$}{
        $t' \leftarrow$ \texttt{(OString $t'$)}\;
      }
      \Else{
        $t' \leftarrow$ \texttt{(OBoolean $t'$)}\;
      }
    }
    \For{$d' \leftarrow (\depth(t')+1)..d$} {
      $t' \leftarrow$ \texttt{(Wrap$_{d'}$ $t'$)}
    }
    \Return{$t'$}
    \end{algorithm}
  \end{minipage}
  \hfill
  \begin{minipage}{0.44\textwidth}
    \begin{algorithm}[H]
      \SetKwInOut{Input}{input}\SetKwInOut{Output}{output}
      \caption{Unwrap(t,d)}\label{alg:unwrap}
    \Input{$t \in \STerms$, $d \in \Nat$}
    \Output{$t' \in \STerms$}
    \BlankLine
    $t' \leftarrow t$\;
    \For{$d' \leftarrow (\depth(t))..d$} {
      \tcp{$d'$ is descending}
      $t' \leftarrow$ \texttt{(Wrap$_{d'}$ $t'$)} 
    }
    \end{algorithm}
  \end{minipage}
\end{center}

For reference prefix $r$ of depth $d$ accessed with key $k$, we create specific selectors based on the composite type of $r$:
\begin{enumerate}
  \item object: \texttt{(select (obj$_d$ r) k)}
  \item array: \texttt{(seq.nth (arr$_d$ s) s)}
  \item set: \texttt{(ite (select (set$_d$ r) k) k \texttt{Wrap(OUndef,$\depth(k)$)})}
\end{enumerate}

\subsection{Function Calls}
\label{ss:func:t}

Recall from Section~\ref{ss:functions} that a \rego function $f \in \Funs$ is a pair
$(A, \phi)$, where $A = \sig(f) = (A_1, \ldots, A_n)$ is a list of argument type sets (or just types with the extension from Chapter~\ref{ch:typ}) and
$\phi : \Vals^n \to \Vals$ is the concrete mapping.
Function names are terms in $\Terms$; the mapping $\Funs$ associates each name with
its definition.
The return type of $f$, denoted $\ret(f)$, is derived from the type analysis of
Chapter~\ref{ch:typ}.

The encoding of a function call $f(t_1, \dots, t_a) \in \Terms$ follows the general
scheme:
$$\encode(f(t_1, \dots, t_a)) \;=\; \texttt{(}\encode(f)\; \encode(t_1)\; \cdots\; \encode(s_a)\texttt{)}$$
where $\encode(f)$ denotes the SMT symbol corresponding to the \rego function name
$f$\footnote{
  Notice that for the encoding of a function name $f$ with $\encode(f)$, we abuse
  the notation of this signature, which should map to $\STerms$, i.e., Rego terms with
  specific depth, which does not apply to operation names.
}.
% TODO: set encoding to a type
\begin{itemize}
  \item If $\ty_i$ is an atomic type ($\depth(\ty_i) = 0$), the value $s_i$ is first
        reduced to depth $0$ via $\texttt{Unwrap}(s_i, 0)$, and then the corresponding
        field accessor is applied to extract the raw SMT sort: \texttt{(num $s_i$)} for
        $\Int$, \texttt{(str $s_i$)} for $\Str$, and \texttt{(bool $s_i$)} for $\Bool$,
        yielding a term of depth $-1$ as defined in the Values subsection.
  \item If $\ty_i$ is a composite type, $\texttt{Wrap}(s_i, \depth(\ty_i))$ is applied,
        yielding a term of depth $\depth(\ty_i)$.
\end{itemize}

\paragraph{Built-in functions.}
As noted in Section~\ref{ss:functions}, infix operators such as \texttt{+} or \texttt{<}
are compiled to their function form by the OPA compiler; consequently, the transformation
operates uniformly on function call terms.
The mapping $\encode(f_N)$ for all supported built-in operations is given by
Table~\ref{t:builtins}.

\begin{table}[h]
  \centering
  \caption{Definition of $\encode(f_N)$ for supported Rego built-in operations.}
  \label{t:builtins}
  \begin{tabular}{ll}
    \hline
    \textbf{Rego operation} & \textbf{\smtlib term} \\
    \hline
    \texttt{plus}, \texttt{minus}, \texttt{mul}, \texttt{div} & \texttt{+}, \texttt{-}, \texttt{*}, \texttt{/} \\
    \texttt{gt}, \texttt{gte}, \texttt{lt}, \texttt{lte}     & \texttt{>}, \texttt{>=}, \texttt{<}, \texttt{<=} \\
    % \texttt{concat}                                            & \texttt{str.++} \\
    \texttt{contains}                                          & \texttt{str.contains} \\
    \texttt{startswith}, \texttt{endswith}                     & \texttt{str.prefixof}, \texttt{str.suffixof} \\
    \texttt{indexof}                                           & \texttt{str.indexof} \\
    \texttt{substring}                                         & \texttt{str.substr} \\
    \hline
  \end{tabular}
\end{table}

\paragraph{Equality and inequality.}
The equality and unification operators (\texttt{==} and \texttt{=}), as well as
inequality (\texttt{!=}), are treated as a special case.
Rather than extracting the operands to their atomic sorts, both sides are wrapped to a
common depth $d = \max(\depth(s_1), \depth(s_2))$ using \texttt{Wrap} before the
comparison is emitted.
Equality is then encoded as \texttt{(= $s_1$ $s_2$)} and inequality as
\texttt{(not (= $s_1$ $s_2$))}.

\section{Expressions}
\label{s:expr:t}
%%=============================================================

As defined in Section~\ref{ss:head-body}, the expressions $(e_1, \dots, e_n)$ in a rule body $B$ either represent direct conditions, or introduce local variables to the body's scope.
During the process of encoding expressions we need to keep a track of: 1) the \emph{proposition} $\Props$ conjugates the encodings of all direct conditions and 2) the local variable definitions $\LocDefs$.
This section describes the process of encoding these two types into SMT.

%%=============================================================
\subsection{Conditional Expressions}
\label{ss:expr:val}
%%-------------------------------------------------------------

An expression $e$ is \emph{conditional} when it does not introduce a local variable definition to the given context $\Context$.
The encoding of these expressions $\encode(e)$\footnote{
  Since the conditional expressions are representable by a single term, the function $\encode$ is directly applicable to them.
} is appended to $\Props$, the list of propositions of the given rule.

\paragraph{Single-term and Function Call Expressions.}
When $e$ is a single term $t \in \Terms$, or a function call expression not in assign form (Section~\ref{ss:functions}), its contribution to $\Props$ is the SMT encoding of the \emph{holdability} condition $\Holds$ defined in section~\ref{s:exprs}.
For $s = \encode(t) \in \STerms$ with inferred type $\ty = \typof(s)$, the encoding of $\Holds(s)$ is the conjunction of:
\begin{itemize}
  \item \texttt{(not (is-OUndef $\texttt{Unwrap}(s, 0)$))}, if $\Undef$ is among the possible types of $s$,
  \item \texttt{(bool $\texttt{Unwrap}(s, 0)$)}, if $\Bool$ is among the possible types of $s$.
\end{itemize}
For such crafted encoding of condition $s$, the proposition $\Props$ is then updated to \texttt{(and $\Props$ s)}
If neither condition applies, the encoding is \texttt{true}, reflecting that values of other types always hold.

\paragraph{Equality.}
When $e$ is an equality (also called unification) expression $x = t$, where $t \in \Terms$ and $x \in \Context$, it contributes an equality proposition to $\Props$, encoded as described in section~\ref{ss:func:t}.
If $x \notin \Context$, the expression instead creates a local variable definition and no proposition is conjugated with $\Props$.

%%=============================================================
\subsection{Local Variable Definitions}
\label{ss:expr:let}
%%-------------------------------------------------------------

During the translation, a \emph{definition context} $\Context \subseteq \Locals$, initially empty, records which local variables have already been defined in the current body.
Additionally, we keep an ordered list $\LocDefs$ of all local variable definitions:

A \emph{local variable definition} $d = (x, s) \in \Vars \times \STerms$ pairs a variable name with an SMT value.
Whenever a definition is created, the context is extended: $\Context \leftarrow \Context \cup \{x\}$.
Definitions arise from two sources.

\paragraph{Equality as assignment.}
When $e_i$ is the equality expression $x = t$ for $x \notin \Context$, the definition $(x,\ \texttt{Wrap}(\encode(t),\, \depth(x)))$ is appended to $\LocDefs$.
The wrapping to $\depth(x)$ ensures the assigned value has the sort declared for $x$ by the type analysis.

\paragraph{Function call in assign form.}
As described in section~\ref{ss:functions}, a function $f$ of arity $a$ may be called in assign form by supplying the return variable as an additional $(a+1)$-th argument.
In such case, the definition $(x,\, \texttt{Wrap}(\encode(f(t_1, \dots, t_a)),\, \depth(\ref(f))))$ is appended to $\LocDefs$, where $f_R$ is the inferred return type of $f$.\footnote{
  Functions are in the assign form $f(t_1, \dots, t_a, t_r)$ only when $t_r \notin \Context$.
  This is an implicit property of the \rego compilation.
}

\section{Rules}
\label{s:rules:t}
%%=============================================================

This section describes the transformation of \rego rules into \smtlib.
As established in Chapter~\ref{ch:form}, rules can be of four types: complete, accumulating, function, and default.
We limit this transformation only to complete and default rules, since they are the main focus of the analysis presented by this paper.
Default rules are not emitted directly, but serve as a preparatory step by establishing the fallback value used during the encoding of other rules (section~\ref{ss:rules:body}).
For the current state of the transformation, we further assume that each variable with a complete definition is associated with exactly one rule; the handling of multiple rules for the same head is discussed later.

%%=============================================================
\subsection{Rule Body Encoding}
\label{ss:rules:body}
%%-------------------------------------------------------------

For each rule $(h, B)$, the body translation of $\BodyCond(B)$ yields a pair $(\Props, \LocDefs)$ as described in section~\ref{s:expr:t}, with a fresh definition context $\Context$.
% The body value $\BodyVal(B)$ is encoded as $\encode(\BodyVal(B)) \in \STerms$.
% Together, the body is represented as the \smtlib if-then-else construct:
% $$\texttt{ite}(\Props,\; \encode(\BodyVal(B)),\; \mathit{fallback})$$
% where $\mathit{fallback}$ is determined as described in the following section.
% The local variable definitions $\LocDefs = (d_1, \dots, d_k)$, where $d_i = (x_i, s_i)$, are then wrapped around this entire expression as nested \texttt{let}-bindings, such that $x_i$ is in scope for all subsequent definitions $d_{i+1}, \dots, d_k$ and for the \texttt{ite} expression itself.

\begin{algorithm}[H]
  \SetKwInOut{Input}{input}\SetKwInOut{Output}{output}
  \caption{$\encodeb(B,\mathit{fallback})$}\label{alg:body}
  \Input{$B$, $\mathit{fallback} \in \STerms$}
  \Output{$t \in \STerms$}
  \BlankLine
  $\Context = \{\}$\;
  $\Props = \true$\;
  $\LocDefs = ()$\;
  \For{$e \in \BodyCond(B)$\label{alg:body:for}} {
    \uIf {$e{:}\; x = t \land x \notin \Context$} {
      $\texttt{append}(\LocDefs,(x,\encode(t)))$\;
      $\Context \leftarrow \Context \cup \{x\}$
    } \uElseIf {$e{:}\; f(t_1,\ldots,t_n,x) \land $\texttt{arity}$(f) = n$\tcc*[r]{function in assign form}} {
      $\texttt{append}(\LocDefs,(\encode(x),\encode(f(t_1,\ldots,t_n))))$
    } \Else {
      $\Props \leftarrow $(\texttt{and} $\Props$ $\Holds(\encode(e))$)
    }
  }
  $t \leftarrow $\texttt{ite}($\Props,\; \encode(\BodyVal(B)),\; \mathit{fallback}$)\label{alg:body:ite}\;
  \For{$(x,v) \in \texttt{reversed}(\LocDefs)$\tcc*[r]{wrapping with local variable definitions}} {
    $t \leftarrow $ (\texttt{let} (($\encode(x)$ $v$)) $t$)
  }
  \Return{$t$}
\end{algorithm}

We denote the encoding of body $B$ into SMT with $\encodeb(B)$; this function is defined by the Algorithm~\ref{alg:body}.
In this algorithm, the variables are named in accordance to the declarations from the Section~\ref{ss:expr:val}: that is the context $\Context$ containing all defined local variables, the list local variable definitions $\LocDefs$, and the proposition $\Props$.

These variables are iteratively refined throughout the processing of all body expressions, noted by the \texttt{for} loop starting at line~\ref{alg:body:for}.
The output SMT encoding $t$ is then set to the if-then-else construct (line~\ref{alg:body:ite}), informally reading: \textit{if given conditions hold, return the specified value; and return the fallback otherwise.}

Since the propositions may rely on local variables, we introduce them to the current value of $t$ by wrapping it with the \texttt{let} statements.
We iterate them in the reversed order, since local variables may rely on the ones defined prior.
This is also the reason why need to keep the local definitions ordered (by using a list and not a set).

The encoding of a list of bodies $\Bodies = (B_1,\ldots,B_n)$, denoted with $\encodeB$, is then defined as:
$$\encodeB(\Bodies,\textit{fallback}) = \encodeb(B_1,\encodeb(\cdots\encodeb(B_n,\textit{fallback})\cdots)$$
This means that we firstly encode the last body with $\encodeb(B_n,\textit{fallback})$ and pass this value as the fallback to the encoding of $B_{n-1}$.
Doing this iteratively up until the encoding of $B_1$ equals $\encodeB(\Bodies,\textit{fallback})$.

\subsection{Rule Encoding}
\label{ss:rules:encode}
%%-------------------------------------------------------------

Given a rule $r \in \Rules$, we set its transformation into SMT $\encodeR(r)$, w.r.t. its type, as follows:

\subsubsection{Default Rules}
Since default rules contain, by the definition from Section~\ref{ss:default}, a single body $B$ with no conditions, we only set the default value of its head $h$: $\Def(\RuleRef(h)) = \BodyVal(B)$.
This means that the encoding of default rules does not contribute directly with any SMT code.

\subsubsection{Complete Rules}
For a complete rule $r = (h,\Bodies)$, we try to find its encoding.
A naive approach would be to simply assert, that the value of $h$ equals the value given by $\encodeB(\Bodies,\Def(\RuleRef(h)))$, i.e., the encoding of its bodies, falling back to the default value of $h$.

This approach has a big drawback:
When multiple complete rules share the same head $h$, such an encoding introduces a problem we call a \emph{false collision}.
Each rule produces an assignment for $\RuleRef(h)$, which potentially defaults to the fallback value $\Def(\RuleRef(h))$.
If one rule fails while another succeeds, the failing rule still asserts $\RuleRef(h) = \Def(\RuleRef(h))$, which conflicts with the value assigned by the succeeding rule.
This is a spurious conflict: the policy itself contains no collision, but the encoding introduces one.

To resolve this, we instead encode each complete rule $(h,\Bodies)$ into the assertion that the variable given by $h$ equals $\encodeB(\Bodies,\encode(\RuleRef(h)))$.
This means, that if all bodies in $\Bodies$ fail, the assertion reduces to $\RuleRef(h) = \RuleRef(h)$, a tautology that contributes no constraint.
Real conflicts are preserved: if two bodies both hold and assign different values $v_i \neq v_j$, the resulting pair of assertions $\RuleRef(h) = v_i$ and $\RuleRef(h) = v_j$ remains correctly unsatisfiable.

The default value must then be handled by a separate assertion.
Let $\Rules_h = \{r_1, \dots, r_m\}$ be all complete rules of head $h$, and let $\Props_i^j$ denote the body proposition of the $j$-th body of rule $r_i$.
We define $\AllProps_h = \bigvee_{i=1}^{m} \bigvee_{j} \Props_i^j$ as the disjunction of all body propositions across all the rules of $h$.
In addition to the encodings of individual rules from $\Rules_h$, it is asserted that
\[
  \RuleRef(h) =
  \begin{cases}
    \RuleRef(h) & \text{if } \AllProps_h, \\
    \RuleDef(\RuleRef(h))   & \text{otherwise.}
  \end{cases}
\]
This means that the fallback value is \emph{not} assigned if there is any body with satisfied conditions.

\begin{example}
  Consider the following rules for head $x$ with $B1,B2,B3$ being non-empty rule bodies:
\begin{lstlisting}[language=Rego]
default x := d
x := v1 if B1 else := v2 if B2
x := v3 if B3
\end{lstlisting}
  The three emitted assertions are:
\begin{lstlisting}[language=SMT,escapechar=|]
(assert (= x (ite (or B1 B2 B3) x d)))
(assert (= x (ite B1 v1 (ite B2 v2 x))))
(assert (= x (ite B3 v3 x)))
\end{lstlisting}
  In this example, we provided the encoding of the fallback value as the first SMT assertion.
  When only $B3$ holds, both the first (default) and the second assertions reduce to $x = x$ and the third assigns $x = v3$.
  When none of the bodies holds, only the first assertion generates a constraint: $x = d$.
\end{example}
