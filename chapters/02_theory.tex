\section{Rego Policy Language}
\label{sec:rego}
%%=============================================================

This section describes \rego, the policy language used by \emph{Open Policy Agent} (\emph{OPA}).
We introduce the OPA query model and the structure of \rego policies at an intuitive level.
A more formal specification of the policies are presented in Chapter \ref{ch:form}.
To anchor the discussion, consider the policy shown in Figure~\ref{fig:rego}.

\begin{figure}
  \label{fig:rego}
  \begin{lstlisting}[language=Rego,escapechar=|]
package example

reachable_roles := array.concat(data.default_roles, input.roles) |\label{fig:rego:call}|

user_permissions contains permission if { |\label{fig:rego:line:set-rule}|
    some role in reachable_roles |\label{fig:rego:some_decl}|
    some permission in data.permissions[role] |\label{fig:rego:line:ref}|
}

default allow := false |\label{fig:rego:line:default}|

allow if input.action.name in user_permissions |\label{fig:rego:alias-use}|
\end{lstlisting}
  \caption{Example \rego policy.}
\end{figure}

The policy merges role lists from \texttt{input} and the \texttt{data} document into \texttt{reachable\_roles} (line~\ref{fig:rego:call}), collects every permission granted to those roles into the set \texttt{user\_permissions} (lines~\ref{fig:rego:some_decl}--\ref{fig:rego:line:ref}), and sets \texttt{allow} to \true when the requested action name appears in that set (line~\ref{fig:rego:alias-use}).
The role of \texttt{input}, \texttt{data}, and the returned result within the broader OPA query model is described next.

%%=============================================================
\subsection{Open Policy Agent}
\label{ssec:opa}
%%-------------------------------------------------------------

OPA is a general-purpose policy engine that decouples policy decision-making from application logic.
Policy decision-making refers to the evaluation of conditions that determine whether actions such as access requests, configuration changes, or deployment operations should be permitted or denied.

\begin{figure}
    \label{fig:opa-query-graph}
    \centering
    \input{figures/opa-query-graph.tex}
    \caption{Structure of communication between a service and OPA.}
\end{figure}

Figure~\ref{fig:opa-query-graph} depicts the high-level structure of communication between a service and OPA.
The service supplies two structured documents (typically JSON) to OPA: the \texttt{input} document, which represents the current request being evaluated, and the \texttt{data} document, which represents the service's internal state (for example, a list of permitted servers or a role-to-permission mapping).
OPA evaluates a \rego policy against these two documents and returns a response document containing the result.
The service then acts on this response; a common pattern is to authorize a request only when the response contains a specific field, such as \texttt{allow}, set to \true.
OPA does not itself mark a request as authorized or unauthorized; that decision is left to the consuming service.

\rego is the declarative policy language used to express these policies.
It is inspired by Datalog and is designed to reason over structured documents.
A \rego policy specifies the logical conditions under which a conclusion holds; OPA's evaluation engine searches for all variable bindings that satisfy those conditions against the provided \texttt{input} and \texttt{data}.

%%=============================================================
\subsection{Policy Structure}
\label{ssec:rego-structure}
%%-------------------------------------------------------------

Every \rego policy is organized into \emph{modules}.
A module declares the \emph{package} it belongs to, optional \emph{imports} of names from other packages or from the \texttt{input} and \texttt{data} documents, and a set of \emph{rules}.

A \emph{rule} consists of a \emph{head}, which specifies what the rule defines, and an optional \emph{body}, which is a conjunction of conditions.
When all conditions in the body hold, the head contributes a value to the result.
For example, line~\ref{fig:rego:alias-use} of the Figure~\ref{fig:rego} contains a rule with head \texttt{allow} and body with a single expression.
When the body is absent, the rule applies unconditionally, as on line~\ref{fig:rego:call}.
Rules with the same head name are evaluated independently; their contributions are combined to form the final value for that name.

Depending on the form of their head, rules take the following roles:
\begin{itemize}
  \item A \emph{variable definition} rule assigns a scalar or structured value to a name.
    For example, line~\ref{fig:rego:call} in Figure~\ref{fig:rego} assigns the result of a function call to \texttt{reachable\_roles}.
  \item A \emph{boolean rule} is a special case of a variable definition where the assigned value is \true and is omitted from the syntax.
    Line~\ref{fig:rego:alias-use} illustrates this: \texttt{allow} is set to \true when its conditions are satisfied.
  \item A rule whose head contributes an element to a named set accumulates values across all evaluations.
    Line~\ref{fig:rego:line:set-rule} shows this pattern: for each \texttt{permission} for which the body holds, that value is added to \texttt{user\_permissions}.
  \item A rule whose head assigns a value to a key of an object contributes one key-value pair to that object.
    For example, two separate rules \texttt{permissions["read"] if \{ \ldots \}} and \texttt{permissions["write"] if \{ \ldots \}} each contribute one entry; the resulting \texttt{permissions} object collects all entries from all rules whose conditions are satisfied.
  \item A \emph{function definition} rule maps a list of arguments to a value.
    This is a mechanism to specify user-defined functions.
\end{itemize}

%%=============================================================
\subsection{Expressions and References}
\label{ssec:rego-expressions}
%%-------------------------------------------------------------

The body of a rule is a conjunction of \emph{literals}.
Each literal is either an expression, the negation of an expression, or an existential declaration introduced with \texttt{some}.
The body holds when every literal in it is defined and evaluates to a value other than \false.

Expressions that appear in rule bodies include single terms, function calls (written as \texttt{f(a,b)} or using infix notation for built-in operators), and universal quantification over a collection using \texttt{every}.

\rego terms can be \emph{scalars} (\texttt{null}, booleans, numbers, strings), \emph{variables}, \emph{references} into \texttt{input}, \texttt{data}, or locally defined names, \emph{arrays}, \emph{objects}, or \emph{sets}.

A \emph{reference} traverses a structured value step by step.
Dot notation accesses a fixed object key (for example, \texttt{input.user.role}), while bracket notation is used for the rest of key types, including variable keys (for example, \texttt{data.permissions[role]}, as on line~\ref{fig:rego:line:ref} of Figure~\ref{fig:rego}).
If any step in the chain yields no value, the entire reference is \emph{undefined}.

%%=============================================================
\subsection{Undefined and Null}
\label{ssec:rego-undef}
%%-------------------------------------------------------------

A central distinction in \rego is between \emph{undefined} and the scalar value \texttt{null}.

When no rule body for a given name holds, the name produces no result — it is \emph{undefined}.
Undefined is not a value that can appear in the output document; it means the name is absent from the result entirely.

The scalar value \texttt{null}, by contrast, is a concrete JSON value.
It can be stored in a document, passed as a function argument, and compared for equality.
It is used to explicitly represent the absence of information within a value: for example, a built-in function may accept \texttt{null} for an optional parameter to indicate that the caller does not supply a value for it.

The \texttt{default} keyword provides a fallback specifically for the undefined case.
A rule of the form \texttt{default allow := false} assigns \false to \texttt{allow} only when every other rule for \texttt{allow} is undefined.
If any rule for \texttt{allow} applies, the default is ignored.
Line~\ref{fig:rego:line:default} in Figure~\ref{fig:rego} illustrates this pattern.

%%=============================================================
\subsection{Preliminaries}
%%-------------------------------------------------------------

\paragraph{SAT Solving.}
The \emph{Boolean Satisfiability Problem}, categorized as an \emph{NP-complete} problem, decides whether a given propositional formula $\phi$ has a solution.
In such a case, we say that $\phi$ is \emph{satisfiable}, which can also be denoted with $\sat$.
Otherwise, this formula is marked as $\unsat$.
In computer science, deciding this problem is called \emph{SAT solving}, and tools for its automation are called \emph{SAT solvers}.

%%-------------------------------------------------------------
\paragraph{Satisfiability Modulo Theories.}
The defining problem of \emph{Satisfiability Modulo Theories} (\emph{SMT}) is checking whether a given (closed) logical formula $\phi$ is satisfiable, in the context of some background theory $\T$ which constrains the interpretation of the symbols used in $\phi$\cite{smt:sm-theories, smt:first-ord-logic}.
Technically, the SMT problem for $\phi$ and $\T$ is the question of whether there is a model of $\mathcal{T}$ that makes $\phi$ true.
\emph{SMT solver} is a tool that implements a procedure for satisfiability modulo some given theory. 

What sets apart SMT from general automated deduction is that the background theory $\mathcal{T}$ need not be finitely or even first-order axiomatizable, and that specialized inference methods are used for each theory.
By being theory-specific and restricting their language to certain classes of formulas (such as, typically but not exclusively, quantifier-free formulas), these specialized methods can be implemented in solvers that are more efficient in practice than general-purpose theorem provers.

\subsection{SMT-LIB}
%%-------------------------------------------------------------

The \smtlib Standard is an international initiative and specification that defines a common language and infrastructure for interacting with SMT solvers.
\smtlib aims to facilitate research, development, comparison, and benchmarking of SMT solvers by providing rigorous definitions of languages, theories, and interfaces used in the automated reasoning community.
The initiative also supports a large library of benchmark problems written in a standardized format.

The \smtlib standard defines a formal language for writing logical formulas, specifying background theories, defining logics, and interacting with SMT solvers via a command-based interface. The standard’s objectives include: providing a common input/output language for SMT solvers; defining a standard set of sorts, functions, and predicates for background theories; and supporting structured benchmark libraries for experimental evaluation.

SMT-LIB’s language is based on many-sorted (typed) first-order logic with equality, where terms and formulas are strongly typed and structured according to defined sorts such as Bool, Int, and user-defined or theory-specific sorts.
Scripts in the SMT-LIB language consist of commands that declare symbols, assert formulas, query solver actions (e.g., \texttt{check-sat}), and interact with solver responses.
SMT-LIB’s syntax uses S-expressions similar to Lisp to represent terms and commands.

The standard separates concerns into clearly defined components:
\begin{itemize}
    \item \emph{Formula language} — a typed logical language for defining SMT problems.
    \item \emph{Theory declarations} — definitions of sorts and function symbols that form the semantic basis for logical theories (e.g., integers, arrays, bit vectors, strings).
    \item \emph{Logic specifications} — combinations of theory signatures and syntactic restrictions that define classes of admissible formulas.
    \item \emph{Command language} — a textual interface for communicating with SMT solvers, including declaring symbols, asserting constraints, checking satisfiability, and retrieving models.
\end{itemize}

The standard also maintains a catalog of benchmark problems in the SMT-LIB format, grouped by logics and used in community-driven evaluations such as SMT-COMP.
These benchmarks support the systematic assessment of solver performance and feature diverse problem classes across background theories.

The SMT-LIB standard distinguishes between \emph{basic} theories and \emph{combined} theories.
Basic theories, such as the theory of real numbers, the theory of arrays, the theory of fixed-size bit vectors and so on, are those explicitly defined in the SMT-LIB catalog.\footnote{The catalog of basic theories in SMT-LIB is available at \url{https://smt-lib.org}.}
Combined theories are defined implicitly in terms of basic theories by means of a general modular combination operator.
The difference between a basic theory and a combined one in SMT-LIB is essentially operational.
Some SMT-LIB theories, such as the theory of finite sets with a cardinality operator, are defined as basic theories, even if they are in fact a combination of smaller theories, because they cannot be obtained by modular combination.

\subsection{Z3}
\label{sec:z3}
%%-------------------------------------------------------------

\textit{The information about \ziii is taken from \cite{z3} and \cite{z3:web}.}

\ziii is an SMT solver from Microsoft Research with its first external release dating back to 2007.
Its main purpose is solving problems that arise in software verification and analysis.
\ziii integrates support for a variety of theories, with the most prevalent for this work being linear integer arithmetic, strings, and arrays.

\ziii is implemented in C++ and it is designed to be highly extensible, thanks to its
modularity. From a high-level point of view, \ziii integrates:
\begin{itemize}
    \item 
        \emph{Core theory SAT solver.} Davis–Putnam–Logemann–Loveland (DPLL) algorithm based solver of propositional logic. 
        This solver is used to handle equalities and uninterpreted functions.
    \item 
        \emph{Satellite solvers.}
        Specialized theory solvers.
    \item 
        \emph{E-matching abstract machine.}
        This component finds instantiations of quantified formulas that lead to a satisfiable solution.
\end{itemize}

\begin{figure}
    \label{fig:z3-system-arch}
    \centering
    \includegraphics[width=0.75\textwidth]{figures/z3-system-arch.png}
    \caption{System architecture of Z3.}
\end{figure}

A schematic overview of the structure of \ziii is shown in Figure~\ref{fig:z3-system-arch}.
Essential components of \ziii are then described as follows:

%%-------------------------------------------------------------
\paragraph{Input.}
It is possible to interact with \ziii using either a textual format or a binary API.
As mentioned in \cite{z3:web} the textual input can appear in several different forms with the most notable one being SMTLIB2 format, which uses a LISP-like syntax.
Programmatic interaction with this tool is possible through an API from Python, C, C++, Go, Java, and other languages.

%%-------------------------------------------------------------
\paragraph{Simplifier.}
To offer the maximum performance, input formulas are first simplified in an incomplete, but efficient process.
To simplify a formula, this component applies standard algebraic reduction rules.
For example $p \land true$ can be reduced to just $p$.
In this process, the simplifier even tries to identify equational definitions (such as $x = 4$) within a context and using the given definition, it then reduces the remaining formula.
For example, $x = 4 \land q(x)$ can be this way reduced to $x = 4 \land q(4)$.

%%-------------------------------------------------------------
\paragraph{Compiler.}
This component takes a simplified abstract syntax tree representation of the input formula and converts it into a different data structure.
Such data structure comprises a set of clauses and congruence-closure nodes.

%%-------------------------------------------------------------
\paragraph{Atoms.}
Atoms, or atomic formulas, are formulas, which cannot be further decomposed into simpler logical components.
Atoms can be either equalities or theory-specific atoms (for instance an arithmetical inequality).

%%-------------------------------------------------------------
\paragraph{Congruence Closure Core.}
The congruence closure core receives truth assignments to atoms from the SAT solver.
Such asserted equalities are then propagated using a data structure called E-graph, with nodes in such a graph pointing to one or more theory solvers.
A merge of two nodes is propagated to all theory solvers pointed to by the given nodes.
The core also propagates the effects of the theory solvers.
Such effects can range from inferred equalities to assignment of atoms to true or false.
In the case of non-convex theories (i. e., theories for which quantifier elimination and other automated reasoning procedures are complicated or impossible), the theory solvers can also produce fresh atoms.

%%-------------------------------------------------------------
\paragraph{Theory Solvers.}
\ziii’s ability to solve constraints of a specific theory comes from its integration with a solver for the given theory.
These specialized solvers are called theory solvers or satellite solvers.
As shown in the Figure \ref{fig:z3-system-arch}, solvers are used to produce new atoms for given assignment from the \ziii core, i.e., the congruence closure core.

%%-------------------------------------------------------------
\paragraph{E-matching Engine.}
This engine is used for reasoning over quantifiers, where \ziii combines a well known approach with new algorithms described in \cite{z3:e-match}.
In this process, it operates over the E-graph data structures and passes generated clauses to the SAT solver.

%%-------------------------------------------------------------
\paragraph{SAT Solver.}
\ziii leverages the power of a state-of-the-art SAT solver which integrates standard search pruning methods.
It is used to control boolean case splits generated by the \ziii core (sometimes with the extra step of E-matching).

\gap

The components of \ziii offer a special set of tools and techniques which help the SMT solver stand out amongst others, the most significant of which are:

%%-------------------------------------------------------------
\paragraph{Deleting Clauses.}
During quantifier instantiation, clauses containing new atoms are as a side-effect produced into the search space.
When such a clause is useless in closing branches, it is garbage collected together with its atoms and terms.
Conflict clauses are not deleted, but retained as a side-effect.

%%-------------------------------------------------------------
\paragraph{Relevancy Propagation.}
In practice, several atoms appearing in a goal of an SMT solver are irrelevant, or so-called \emph{don’t cares}.
For expensive theories, \ziii ignores such atoms and inference rules.
To distinguish relevant atoms from don’t cares, \ziii uses algorithm described in \cite{z3:rele}.

%%-------------------------------------------------------------
\paragraph{Model Generation.}
\ziii has the ability to produce models as part of the output.
Such models assign values to the constants in the input and generate partial function graphs for predicates and function symbols.

\gap

\ziii has established itself as a state-of-the-art SMT solver since its release in 2007.
It has remained with this title to this day, because of its stability, efficiency and modularity.
It also supports a variety of non-standard theories, such as Array theory.
For these reasons, we have decided to focus the SMT code generation presented in the next chapters onto it.

%%=============================================================
\subsection{Supported Theories in Z3}
%%-------------------------------------------------------------

Even with its emphasis on modularity and ease of extension, \ziii supports most of
the commonly used theories out-of-the-box.\footnote{
  The list of all supported theories is interactively presented at
  \url{https://microsoft.github.io/z3guide/docs/theories/Arithmetic}, which was the
  main source for this passage.
}
The most relevant theories to this work are:

%%-------------------------------------------------------------
\paragraph{Uninterpreted Functions.}
This term refers to functions that do not belong to the signature of any specific
theory, and whose behavior is determined solely by the constraints imposed on their
outputs.
Constants are commonly declared as uninterpreted functions with no arguments.
In \smtlib, such declaration looks as the following:
\begin{lstlisting}[language=SMT]
(declare-fun x () Int)
\end{lstlisting}
which denotes a variable $x$ of the builtin integer type.
Any Rego variable or user-defined function whose semantics is not fully determined
by the encoding is naturally represented as an uninterpreted function symbol,
with the policy body providing the only constraints on its output.

%%-------------------------------------------------------------
\paragraph{Arithmetic.}
\ziii provides built-in support for integers (\texttt{Int}) and real numbers (\texttt{Real}).
These correspond to their mathematical representations and are not limited by any fixed bit-width.
Basic arithmetic operators are available using standard notation such as
$+, -, *,$ etc.
For integer constants $a, b, c$, the relation $a < b + c$ is expressed as:
\begin{lstlisting}[language=SMT]
(assert (< a (+ b c)))
\end{lstlisting}
Note that function and operator applications follow a prefix notation.

%%-------------------------------------------------------------
\paragraph{Strings.}
\ziii provides support for strings, including standard operations such as
concatenation, length computation, substring search, and character access.
These operations are available under the \texttt{str.} prefix.
For example, enforcing that two strings $a$ and $b$ have equal length can be written as:
\begin{lstlisting}[language=SMT]
(assert (= (str.len a) (str.len b)))
\end{lstlisting}
Regular expressions can be manipulated using operations with the \texttt{re.} prefix.
The underlying decision procedure for the combined theory of strings and regular expressions used in \ziii is described in~\cite{smt:strings}.

%%-------------------------------------------------------------
\paragraph{Arrays.}
In SMT, an array is viewed as a total function from index sort $\tau_I$ to value sort $\tau_V$.
Intuitively, an array assigns a value $e \in \tau_V$ to every index $i \in \tau_I$.

Arrays support the basic operations \texttt{select} and \texttt{store} for reading and writing, respectively.
These operations are defined by the standard McCarthy axioms~\cite{mccarthy:arrays}:
\begin{itemize}
  \item $\mathsf{select}(\mathsf{store}(A,i,v),i) = v$
  \item $i \neq j \implies \mathsf{select}(\mathsf{store}(A,i,v),j) = \mathsf{select}(A,j)$
  \item $(\forall_i: \mathsf{select}(A,i) = \mathsf{select}(B,i)) \implies A = B$
\end{itemize}
Additionally, constant arrays — where every key maps to the same value $v$ — can be
defined using the function $K$:
$$\forall_i: \text{select(K(v),i)} = v$$
which is provided by \ziii via the \texttt{as-const} operation, taking the array
type and a default value as arguments.
The decision procedure for the Array theory as implemented in \ziii is described
in~\cite{z3:array-theory}.
In the context of this work, the Array theory is used to model Rego objects —
mappings from string keys to values — and Rego sets, which can be represented as
arrays from an element sort to \texttt{Bool}.

%%-------------------------------------------------------------
\paragraph{Sequences.}
While the Array theory models a collection as a total function on an infinite index
domain, \ziii's Sequence theory models ordered, finite lists over an element sort
$\tau$, written \texttt{(Seq $\tau$)}.
Key operations include \texttt{seq.len} (length), \texttt{seq.nth} (indexed access),
\texttt{seq.concat} (concatenation), \texttt{seq.contains}, and \texttt{seq.unit}
(singleton constructor).
For example, asserting that the first element of a sequence $s$ of integers equals
$42$ is written:
\begin{lstlisting}[language=SMT]
(assert (= (seq.nth s 0) 42))
\end{lstlisting}
Notably, \ziii treats the \texttt{String} sort as the special case
\texttt{(Seq Char)}, so strings and sequences share the same solver
backend~\cite{smt:sequences}.

%%-------------------------------------------------------------
\paragraph{Algebraic Datatypes.}
Algebraic datatypes (ADT) allow the declaration of discriminated union types,
where a value belongs to exactly one of a set of named \emph{constructors}, each
carrying zero or more typed fields.
Without ADT support, encoding such a union requires manual type-tag predicates and
explicit disjointness axioms; with \texttt{declare-datatype}, the solver enforces
injectivity, disjointness, and exhaustiveness automatically~\cite{smt:adt-decision}.
As a concrete illustration, consider an optional integer value:
\begin{lstlisting}[language=SMT]
(declare-datatype Optional ((None) (Some (value Int))))
\end{lstlisting}
This introduces two constructors (\texttt{None}, \texttt{Some}), a \emph{selector}
\texttt{value} extracting the integer payload of \texttt{Some}, and
\emph{constructor recognizers} \texttt{is-None} and \texttt{is-Some}.
For example, \texttt{(assert (and (is-Some x) (> (value x) 0)))} constrains a term
$x$ to a positive integer wrapped in \texttt{Some}; the selector \texttt{value} is
well-defined precisely when \texttt{is-Some} holds, and unspecified otherwise.
ADTs also support recursive definitions, which becomes relevant when modeling nested
Rego structures such as arrays of objects.

The quantifier-free fragment of the ADT theory is decidable~\cite{smt:adt-oppen}.
The decision procedure~\cite{smt:adt-decision} is built on top of the congruence
closure engine used for uninterpreted functions, extending it with three
ADT-specific inference rules: \emph{injectivity} ($C(a) = C(b) \implies a = b$),
\emph{disjointness} ($C(\ldots) \neq D(\ldots)$ for distinct constructors $C, D$),
and \emph{acyclicity} (no term may equal one of its own proper subterms).
Plain uninterpreted functions do not enforce any of these properties, so the
extension is essential rather than merely cosmetic.

%%-------------------------------------------------------------
\paragraph{Quantifiers.}
SMT formulas in the quantifier-free (QF) fragment are generally decidable for the
theories considered in this work, but adding unrestricted quantifiers over infinite
domains renders satisfiability undecidable in general~\cite{smt:mbqi}.
\ziii addresses quantified formulas through two complementary mechanisms: the
E-matching engine described in Section~\ref{sec:z3} (see \cite{z3:e-match}), which
instantiates quantified formulas guided by pattern triggers, and Model-Based
Quantifier Instantiation (MBQI)~\cite{smt:mbqi}, which provides a complete
procedure for certain quantified fragments.

%%-------------------------------------------------------------
\paragraph{Theory Combination.}
In practice, an SMT encoding of a Rego formula simultaneously uses Arithmetic,
Strings, Sequences, Arrays, and Algebraic Datatypes.
The Nelson--Oppen combination framework~\cite{smt:nelson-oppen} establishes that
two theories sharing only the equality symbol, both of which are
\emph{stably infinite}, can be combined with no loss of soundness or completeness.
The correctness of this combination procedure is further analysed
in~\cite{smt:tinelli-harandi}.
\ziii's congruence closure core, described in Section~\ref{sec:z3}, is the practical
realization of this framework, propagating equalities across the individual theory
solvers transparently.
